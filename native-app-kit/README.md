# native-app-kit — симметричный релиз-флоу для нативного приложения

Портируемый набор, который делает версионирование приложения **симметричным** серверному
продукту: SemVer-теги, CHANGELOG, релиз одной командой и двусторонний обмен через Pull Request.
Мобильную часть ведёт партнёр; серверную — владелец продукта. Каждый видит изменения другого
и сам решает, что берёт.

## Установка (партнёр, один раз)
Скопировать содержимое этой папки в **корень репозитория приложения**:
```bash
cp native-app-kit/{release.sh,CHANGELOG.md,VERSION} /path/to/app-repo/
cd /path/to/app-repo && chmod +x release.sh
git add release.sh CHANGELOG.md VERSION && git commit -m "chore: релиз-флоу (native-app-kit)"
```

## Как выпускать релиз приложения
```bash
# 1) впиши изменения в раздел «## [Unreleased]» в CHANGELOG.md
# 2) выпусти версию: перенесёт Unreleased→vX.Y.Z, поднимет marketing+build, тег, пуш
./release.sh 1.2.0
# 3) собери и залей в TestFlight (Xcode → Product → Archive → Organizer, или fastlane)
```
`release.sh` сам:
- перенесёт `[Unreleased]` в `CHANGELOG.md` в новую версию с датой;
- выставит `CFBundleShortVersionString = X.Y.Z` и увеличит `CFBundleVersion` (через `agvtool`,
  если проект настроен; иначе подскажет сделать это в Xcode);
- закоммитит, поставит тег `vX.Y.Z`, запушит.

## Двусторонний обмен (ты ⇄ партнёр) — симметрично серверу
- **upstream приложения** — репозиторий партнёра (он мейнтейнер мобильной части).
- **Партнёр → ты:** он выпускает релиз (`./release.sh`), ты видишь `CHANGELOG` и решаешь,
  нужно ли тебе что-то из этого (обычно приложение и сервер релизятся независимо).
- **Ты → партнёр:** свои предложения по приложению отдаёшь **Pull Request**'ом в его репозиторий,
  он ревьюит и решает:
  ```bash
  git checkout -b feat/что-то && git push origin feat/что-то
  gh pr create --repo <ПАРТНЁР>/<APP_REPO> --base main --title "..." --body "..."
  ```
  Он: `gh pr list` · `gh pr view <N> --web` · `gh pr merge <N> --squash` / `gh pr close <N>`.

Полная модель и шпаргалка команд — в серверном `docs/COLLABORATION.md` (та же логика, обе стороны).

## Совместимость версий
Приложение и сервер версионируются **независимо** (у каждого свой `VERSION`/теги). В release-notes
приложения отмечай минимально нужную версию сервера (напр. «требует сервер ≥ 0.2.0»), чтобы не
разъехались. Ломающие изменения API сервера — это `MAJOR` на сервере и явная пометка в обоих CHANGELOG.

## Раздача (вместо серверного update.sh)
У приложения нет «сервера, который тянет обновления» — раздача идёт штатно через **TestFlight**
(бета) и **App Store** (релиз). Тег `vX.Y.Z` = точка сборки. При желании позже прикрутим CI
(GitHub Actions + fastlane) для авто-загрузки в TestFlight по тегу — скажи, добавлю шаблон.
