# Двусторонний обмен версиями (ты ⇄ партнёр)

Как вести общий продукт вдвоём: ты правишь продуктовую часть, партнёр — своё,
и **каждый видит изменения другого и сам решает, что брать**. Модель стандартная —
git «upstream + форк + Pull Request». Ничего самопального: партнёр-разработчик её знает.

## Роли и репозитории
- **upstream** — канонический репозиторий продукта. Мейнтейнер — **ты**. Здесь «истина».
- **форк партнёра** — его копия upstream. На ней крутится его сервер и живут его правки.
- **native-app** — отдельный репозиторий нативного приложения (владелец — партнёр).

Схема потоков:
```
        ты (maintainer)                     партнёр
   ┌───────────────────┐   PR на ревью   ┌──────────────────┐
   │  upstream (истина) │ ◀────────────── │  форк партнёра    │
   │  main + теги vX.Y.Z│ ──────────────▶ │  (его сервер,     │
   └───────────────────┘   update.sh     │   его доработки)  │
                                          └──────────────────┘
```

## Разовая настройка (один раз)
**У тебя (upstream):** это текущий репозиторий. Дай партнёру доступ (Read) или он делает форк.

**У партнёра (на его сервере, после `deploy/install.sh`):**
```bash
cd /opt/friend-claude
git remote add upstream https://github.com/<ТЫ>/<REPO>.git   # канонический продукт
git remote -v   # origin = его форк, upstream = твой продукт
```

## Поток 1 — ТЫ → ПАРТНЁР (ты выпускаешь, он получает)
Ты поправил продукт. Выпуск релиза:
```bash
# 1) впиши, что изменилось, в раздел «## [Unreleased]» в CHANGELOG.md
# 2) выпусти версию (перенесёт Unreleased → vX.Y.Z, поставит тег, запушит)
sudo bash deploy/release.sh 0.2.0
```
Партнёр забирает — с показом «что нового»:
```bash
sudo bash deploy/update.sh      # покажет CHANGELOG + коммиты, спросит подтверждение, применит, перезапустит
```
Он **видит список изменений** (из CHANGELOG) до того, как применить.

## Поток 2 — ПАРТНЁР → ТЫ (он предлагает, ты решаешь)
Партнёр доработал продуктовую часть и хочет отдать тебе. Он **не пушит тебе напрямую** —
делает Pull Request, а ты решаешь, брать ли:
```bash
# у партнёра, в его форке:
git checkout -b feat/что-то
# ...правки, коммиты...
git push origin feat/что-то
gh pr create --repo <ТЫ>/<REPO> --base main --title "..." --body "что и зачем"
```
```bash
# у тебя (ревью и решение):
gh pr list                      # входящие предложения
gh pr view <N> --web            # посмотреть дифф/описание
gh pr checkout <N>              # проверить локально
gh pr merge <N> --squash        # взять к себе   ИЛИ   gh pr close <N> — отклонить
```
Так ты **видишь каждую его правку и сам решаешь**, что берёшь в upstream.

## Правила, чтобы не было боли
- **Всё меняемое — через ветки и PR** (обе стороны), в `main` — только через merge.
- **CHANGELOG обязателен**: перед релизом впиши изменения в `[Unreleased]`. Это то, что
  партнёр читает в `update.sh`. Без записи — партнёр не поймёт, что поменялось.
- **SemVer**: `MAJOR.MINOR.PATCH` — ломающее/новое/фикс. Тег = релиз.
- **Секреты и состояние не коммитим** (`.env`, `*.session`, `state.json`, `schedules.json`,
  `session_calib.json`, память помощницы) — они у каждого свои (см. `.gitignore`).
- **Свои локальные правки** на сервере партнёра `update.sh` сам прячет в `git stash`;
  если у него разошлись коммиты — он делает `git rebase upstream` или оформляет PR.
- **Нативное приложение** — отдельный репозиторий партнёра, свой `VERSION`/CHANGELOG/теги
  и та же логика. Готовый релиз-флоу для него — в `native-app-kit/` (положить в корень репо
  приложения): `release.sh` (bump marketing+build версии, CHANGELOG, тег, пуш) + шаблон CHANGELOG.
  Твои предложения по приложению — PR'ом в его репозиторий, он ревьюит и решает. Раздача — TestFlight/App Store.

## Шпаргалка
| Хочу | Команда |
|---|---|
| Выпустить релиз (ты) | `deploy/release.sh X.Y.Z` |
| Получить обновление (партнёр) | `deploy/update.sh` |
| Предложить правку в upstream | `gh pr create --repo <ТЫ>/<REPO> --base main` |
| Посмотреть входящие предложения | `gh pr list` · `gh pr view <N> --web` |
| Взять правку к себе | `gh pr merge <N> --squash` |
| Отклонить | `gh pr close <N>` |
| Какая у меня версия | `cat VERSION` |
| Что нового доступно | `deploy/update.sh` (покажет и спросит) |
